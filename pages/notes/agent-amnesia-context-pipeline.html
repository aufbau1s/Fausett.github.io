Your AI agent does not have amnesia — your context pipeline is broken

One-liner (what’s the point?)

We had a 400k-token model and a 10-message thread… and Hank still “forgot” what we were doing. Here’s why—and the three Slack settings that fixed it.

The problem: context loss that shouldn’t happen

Day 1 was fun, but it had a classic AI-lab smell:

We had a solution, but no problems.

So on Day 2 we tried the obvious next step: give Hank access to more of our real life (Slack, Obsidian, the daily operating system).

Within an hour, we hit something that felt impossible: Hank was losing context mid-conversation.

A real example looked like this:

Lewis: “Can you help organize the tags in Obsidian?”

Hank: “I can. Quick question: do you want me to retag everything (including tags you already made), or just focus on new tags?”

Lewis: “Let’s focus on the new tags.”

Hank: “Awesome. What exactly do you want me to add tags to? Files, folders, or notes?”

That last question is the tell.

It’s not wrong—but it’s the kind of ambiguity that only appears when the agent is missing the earlier intent.

Why a huge context window doesn't guarantee memory

Context window = how many words the model can hold at once.

But the model doesn’t automatically receive your whole Slack history. OpenClaw has to choose what previous messages to include when it builds the prompt.

So you can have a 400k-token model, but only feed it the last ~50 Slack messages (or worse, miss the root message in a thread). When that happens, the model “forgets” because it never saw the info in the first place.

The root cause: Slack history was being assembled wrong

The bug wasn’t “GPT forgot.”

The bug was: Slack context was being pulled in a way that sometimes excluded the most important message(s)—especially the thread’s root message and/or relevant channel context.

OpenClaw gives you a few knobs that control this:

1) channels.slack.historyLimit

How many previous Slack messages OpenClaw loads into context.

  • Default is typically 50.
  • We bumped ours to 200 for debugging.

Tradeoff: higher = better continuity, but more tokens/cost.

2) channels.slack.thread.inheritParent

Whether the thread root message is included as context.

Important caveat: if this is false, the parent only shows up if it’s within the last historyLimit messages. That means you can end up in a thread where the most important message (the original request) is missing.

We saw noticeably better behavior with this set to true.

3) channels.slack.thread.historyScope

Where the history is pulled from.

  • thread = only messages in the thread
  • channel = thread + surrounding channel messages (useful when people reply in channel, link things, or the thread lacks context)

We changed ours to channel.

The settings that fixed it for us

This set eliminated the “amnesia / ambiguity” loop:

channels:
  slack:
    historyLimit: 200
    thread:
      inheritParent: true
      historyScope: channel

If you want to optimize for cost later, walk historyLimit down (200 → 150 → 100) and see when it breaks.

What “good” looks like: a quick diagnostic

If the assistant asks a question that was answered 1–3 messages ago, it’s almost always a prompt-assembly / history selection problem, not a model capability problem.

The fix is usually: ensure the root message is included + increase historyLimit + choose historyScope intentionally.

Loose end: why Hank sometimes replies twice (30 minutes apart)

After we fixed the memory issue, we noticed a separate weirdness:

Sometimes Hank would send a second response much later, like it was delayed.

That’s next on the debugging list.

Why the agent sometimes replies twice

Likely causes: tool retry / webhook duplicate delivery / background job replay / Slack event ack timing.

Next step: capture message IDs + gateway logs for a single incident and confirm whether the second reply is a retry, a separate agent turn, or a Slack delivery artifact.
